个人的理解 MySQL：深入剖析 MVCC 与锁机制

在关系型数据库中，事务的隔离性（Isolation）与并发性能往往是一对不可调和的矛盾。如果为了极致的数据安全性，每次读写都加重锁，系统吞吐量将断崖式下跌；如果完全不加锁，又会出现脏读、不可重复读和幻读等并发一致性问题。

MySQL InnoDB 存储引擎之所以能兼顾高并发吞吐与ACID 事务安全性，其核心功臣正是：MVCC（Multi-Version Concurrency Control，多版本并发控制） 与 行级锁机制 的完美协同。

一、为什么需要 MVCC？它解决了什么？

在没有 MVCC 的传统数据库设计中，并发控制主要依赖纯粹的锁机制：

  • 读-读并发：加共享锁（S 锁），相互不阻塞；
  • 写-写并发：加排他锁（X 锁），必须串行等待，防止脏写；
  • 读-写 / 写-读并发：读会阻塞写，写也会阻塞读。只要有事务在更新某行数据，其他所有查询该行的事务都要排队等待。

这种读写互斥的设计极大地制约了数据库的高并发性能。而在互联网业务场景中，数据库通常是“读多写少”（读操作往往占比 80%~90% 以上）。

MVCC 解决的核心痛点：

  1. 读写不再冲突（核心）：实现了“写不阻塞读，读也不阻塞写”，查询操作（快照读）完全不需要申请锁。
  2. 消除了大部分锁竞争开销：极大提升了数据库在高并发读写场景下的整体吞吐量。
  3. 低成本实现隔离级别：在不依赖锁机制的前提下，纯靠多版本视图优雅解决了 RC（读已提交） 下的脏读，以及 RR（可重复读） 下的不可重复读与快照读幻读。

二、MVCC 的底层实现三大基石

MVCC 并不是凭空产生的，它在 InnoDB 内部由三大核心模块相互支撑实现：

1. 三大隐式隐藏字段

InnoDB 会在每行聚簇索引记录后隐式添加几个系统字段：

隐藏字段名 占用空间 作用与含义
DB_TRX_ID 6 字节 记录最后一次插入或修改该行记录的事务 ID（自增生成）。
DB_ROLL_PTR 7 字节 回滚指针，指向该行记录写入 Undo Log 中的上一个历史版本。
DB_ROW_ID 6 字节 行 ID。若表没有主键且没有唯一非空索引，InnoDB 会生成该隐藏字段作为聚簇索引主键。

2. Undo Log（回滚日志）与版本链（Version Chain）

每次对行记录进行修改（UPDATE 或 DELETE）时：

  1. 事务修改前，InnoDB 会把修改前的旧数据完整记录到 Undo Log 里。
  2. 将当前最新行中的 DB_ROLL_PTR 指针指向刚才写入 Undo Log 的旧记录。
  3. 如果又有新的事务更新该行，继续写入 Undo Log 并向前链接。

由此，以 DB_ROLL_PTR 为链指针，以时间倒序形成了一条单向链表，这就是版本链：

注意： 对于 DELETE 操作，在 InnoDB 中其实等同于一次特殊的 UPDATE：它会在记录头信息中将 delete_mask 标记置为 1，并将 DB_TRX_ID 更新为执行删除的事务 ID，同样挂载在版本链中，直到未来没有事务引用时才由后台 Purge 线程真正物理清除。

3. ReadView（一致性读视图）与可见性判断规则

当事务执行“快照读”时，InnoDB 会为该事务瞬间抓取一个数据结构——ReadView。

ReadView 内部包含四个核心参数：

  1. creator_trx_id：创建该 ReadView 的当前事务自身的事务 ID。
  2. m_ids：生成 ReadView 瞬间，系统中所有**活跃（已开启但尚未提交）**的事务 ID 列表。
  3. min_trx_id：m_ids 中的最小值（当前最早开启且未提交的事务 ID）。
  4. max_trx_id：系统即将分配给下一个事务的 ID（当前系统已出现的最大事务 ID + 1）。

核心可见性判断数轴与算法：

当事务去读取版本链上的某条记录时，会取出该版本的 DB_TRX_ID 进行依次比对：

  • 规则 1（自改可见）：如果 DB_TRX_ID == creator_trx_id，说明是自己事务修改的数据，可见。
  • 规则 2（早期提交）：如果 DB_TRX_ID < min_trx_id，说明修改该版本的事务在生成视图前早就提交了，可见。
  • 规则 3（未来事务）：如果 DB_TRX_ID >= max_trx_id，说明修改该版本的事务是在当前视图创建之后才开启的，不可见。
  • 规则 4（活跃区间）：如果 min_trx_id <= DB_TRX_ID < max_trx_id：
    • 若 DB_TRX_ID 存在于 m_ids 列表中，说明创建视图那一刻该事务仍处于活跃状态未提交，因此不可见；
    • 若 DB_TRX_ID 不在 m_ids 中，说明该事务虽然晚于 min_trx_id 开启，但在生成视图前已经顺利提交，因此可见。

如果判断为不可见，就沿着该记录的 DB_ROLL_PTR 顺流而下找上一个版本，重复上述判断，直到找到第一个可见的历史版本为止！

4. RC 与 RR 在 ReadView 上的根本分水岭

为什么同为 MVCC，RC（读已提交）和 RR（可重复读）表现不同？秘密全在 ReadView 生成的时机：

  • RC（Read Committed）：
    事务中每一次执行 SELECT，都会重新生成一个新的 ReadView。
    • 只要其他事务一提交，下一次 SELECT 重新拿到的 m_ids 就移除了那个事务 ID，从而能查到别人的最新提交，导致了“不可重复读”。
  • RR（Repeatable Read）：
    事务仅在第一次执行 SELECT 时生成一个 ReadView，之后的整个事务期间始终复用这同一个 ReadView！
    • 无论别人怎么修改提交，本事务眼里的世界永远定格在第一次查询的那一刻，从而轻而易举保证了可重复读。

三、MVCC 配合下的锁机制：快照读与当前读

MVCC 固然强大，但它只掌管“无锁读取”。在面对写入、更新或要求强一致性的读取时，必须由 锁（Locking） 出场。

1. 快照读 vs 当前读

类型 包含的 SQL 语句 读取方式与机制
快照读（Snapshot Read） 普通 SELECT ... 不加锁，基于 MVCC 读取 Undo Log 版本链上的快照数据。
当前读（Current Read） SELECT ... FOR UPDATE
SELECT ... LOCK IN SHARE MODE
INSERT / UPDATE / DELETE		 强制加锁，必须读取数据的最新版本，且必须加锁防止其他事务并发修改。

关键理解： 执行 UPDATE user SET age = age + 1 WHERE id = 1 时，数据库必须先执行一次“当前读”获取最新版本的数据并加上 X 锁，然后写入新版本。不能在历史版本上做累加，否则会引发丢失更新。

2. 锁的分类与应用

(1) 锁的意图维度

  • 共享锁（S 锁，读锁）：LOCK IN SHARE MODE，允许并发读，阻止其他事务写。
  • 排他锁（X 锁，写锁）：FOR UPDATE、写操作，独占锁定，阻止其他事务加任何 S 锁或 X 锁。
  • 意向锁（IS / IX 锁）：InnoDB 自动添加的表级锁。当要在某一行加行锁前，先在表上打上意向锁记号。其根本目的是：让后续其他事务申请表锁时，无需逐行遍历检查是否有行被锁定，实现 $O(1)$ 时间复杂度快速判断。

(2) 锁的范围维度（InnoDB 行锁三大件）

  • 记录锁（Record Lock）：精准锁在单条索引项上（如精确等值查询唯一索引 WHERE id = 5 FOR UPDATE）。
  • 间隙锁（Gap Lock）：锁住两个索引键之间的开区间 (a, b)，不允许其他事务在此间隙插入（INSERT）新记录。
  • 临键锁（Next-Key Lock）：记录锁 + 间隙锁 的结合体，锁住的是前开后闭区间 (a, b]。
    • InnoDB 在 RR 隔离级别下的默认行锁算法正是 Next-Key Lock！
    • 当执行当前读（如范围查询或写操作）时，通过 Next-Key Lock 锁死记录和记录之间的间隙，从物理上阻止了其他事务插队插入新数据，从而在当前读场景下彻底杜绝了幻读（Phantom Read）。

四、总结与个人感悟

  1. 空间换时间的美学：
    MVCC 本质上是用 Undo Log 的额外存储空间，换取了海量查询操作无需排队加锁的时间效益。
  2. 两套武器协同作战：
    • 面对日常查询，用 MVCC 快照读 跑出极致吞吐；
    • 面对更新修改，用 Next-Key Lock 当前读 严防死守并发安全性。
  3. RR 解决幻读的真相：
    • 快照读通过 ReadView 避免幻读；
    • 当前读通过 Next-Key Lock（间隙锁） 避免幻读。
      两者的巧妙组合，才构筑了 MySQL InnoDB 坚如磐石又健步如飞的并发基石。
